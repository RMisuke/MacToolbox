# 工具开发系统审计与 Agent 接口适配（2026-10）

> 审计对象：`MacToolbox Demo 0.1` 当前仓库（截至 2026-10-19）。
> 目标：判断「工具开发系统是否完整」，补齐每个工具的 CLI，并把 GUI 平台升级为
> 「GUI 编排 + Agent 可直接调用的工具组」。
>
> 结论先行：**开发链路（manifest → 扫描/校验 → 表单 → JobRunner → 协议 → 产物）是完整的，
> 但 Agent/CLI 层几乎为空。** 本轮新增 `mct` 统一 CLI、`toolbox_spec.py` 共享契约、
> `agent` manifest 标准、5 个工具的 CLI（含 2 个原生工具）和 MCP stdio server。

### 2.1 已有能力（完整）

| 层 | 能力 | 评价 |

| 执行 | `run.command + args`、模板变量、进程组、取消、日志落盘 | 成熟 |
| 协议 | stdout JSONL：log/progress/step/artifact/checkpoint/result/error/env | 成熟；`hello` 未实现 |

| 脚手架 | `new_tool.py` + `_template.toolbox` | 成熟 |

### 2.2 主要缺口（本轮前）

1. **没有统一 CLI**：架构文档里的 `ToolboxCLI` 一直是 P3，未实现。
2. **协议工具只有低层 CLI**：`tool.py run --config <json>` 能跑，但 Agent 需要自己：
   发现工具、读 manifest、补默认值、建 jobDir、写 `_meta`、处理 secret、解析 JSONL。
3. **原生工具没有 CLI**：`system.homebrew` 与 `media.image-ocr` 的 `inputs` 为空、无 `run`，
   Agent 完全无法调用。
4. **没有机器可读的工具目录**：没有 `describe`/JSON Schema，Agent 无法知道参数约束。
5. **没有 Agent 元数据标准**：capability、稳定性、超时、检查点策略、只读/幂等、示例均未声明。
6. **结果契约不统一**：CLI 没有稳定的退出码、最终 JSON、`mct-result.json`。
7. **校验规则有两份**：Swift `ToolValidation` 与 Python `tool_lint` 各写一遍，易漂移。
8. **没有 MCP / OpenAI tools 导出**：不能直接接入支持工具调用的 Agent 客户端。
9. **CLI 没有批量/续跑/doctor 聚合**：这些能力只在 GUI 里。
10. **原生工具与协议工具的执行路径分裂**：无法共享同一套 Agent 工具目录。

## 4. 本轮落地的标准接口

### 4.1 分层

```text
Agent / 用户
   │
   ├── bin/mct           统一 CLI（discover/validate/describe/schema/doctor/run/batch/resume/mcp）
   │      │
   │      └── scripts/toolbox_spec.py   共享契约（发现/校验/Schema/Agent 描述/指纹）
   │
   ├── MCP stdio         mct mcp（tools/list + tools/call）
   │
   └── Tool Protocol     <tool>/scripts/tool.py run|doctor|setup --config
          │
          └── 外部 CLI / SDK（ffmpeg、whisper-cli、brew、Vision...）
```

GUI 与 CLI 共享同一份 `tool.json`、同一套输入模型、同一套 JSONL 协议与 jobDir 布局；
CLI 不复制领域逻辑，只做编排。

### 4.2 `agent` manifest 块

每个工具在 `tool.json` 顶层声明：

```json
"agent": {
  "capability": "media.image.convert",
  "description": "给 Agent 看的一句话能力说明",
  "stability": "stable",
  "readOnly": false,
  "idempotent": true,
  "timeoutSec": 900,
  "checkpoint": "never",
  "tags": ["image", "convert", "batch"],
  "outputs": ["image"],
  "examples": [
    {"title": "PNG 转 WebP", "inputs": {"image": "/tmp/a.png", "format": "webp"}}
  ]
}
```

字段说明见 [`新工具开发指南.md`](新工具开发指南.md) 的 Agent 标准一节。
没有 `agent` 的旧工具仍能运行，但 `mct validate --strict` 会报错，且 Agent 目录信息不完整。

### 4.3 统一命令

```bash
bin/mct list --json
bin/mct describe media.image-convert --json
bin/mct schema media.image-convert
bin/mct schema --all --format openai
bin/mct schema --all --format mcp
bin/mct validate --all --strict
bin/mct doctor media.image-ocr --json
bin/mct setup media.image-ocr --json
bin/mct run media.image-convert --input image=/tmp/a.png --input format=webp
bin/mct batch media.image-ocr --input image=/tmp/in --output-dir /tmp/out
bin/mct resume --job ~/Library/.../Jobs/<id>
bin/mct mcp
```

### 4.4 稳定结果与退出码

- 默认 stdout：最终 JSON（含 `ok/status/jobDir/artifacts/error/durationMs`）；
  stderr：人类进度。
- `--jsonl`：stdout 只放 Tool Protocol 事件。
- 每个 jobDir 写 `mct-result.json`。
- 退出码：`0` 成功、`1` 工具失败、`2` 参数/契约错误、`3` 工具不存在、
  `4` 超时、`5` 取消、`6` 等待人工检查点。
- 检查点：非 TTY 默认退出 `6` 并保留 jobDir；人工改完产物后
  `mct resume --job <dir> --checkpoint auto`。

### 4.5 MCP

`mct mcp` 暴露 `initialize`、`tools/list`、`tools/call`、`ping`、`shutdown`。
工具名 = id 的安全化形式（如 `media_image-convert`），`inputSchema` 直接来自 manifest。
MCP 调用默认 `checkpoint=auto`，适合无交互 Agent；需要人工审查时走 CLI。

## 7. 仍需改进（按优先级）

### P1（建议下一轮）

1. **MCP 完整度**：`resources`、`prompts`、进度通知、取消通知、`tools/list` 变更通知。
2. **声明式 `run.mode=steps`**：架构文档承诺但未实现；当前所有工具走 protocol。
3. **CLI 全局调度**：`mct batch --jobs` 只做本地并发，未复用 Swift `ResourceScheduler`
   的 GPU/网络容量；多 Agent 并发时可能超卖。
4. **`requirements` 自动探测**：目前仍需工具在 `doctor` 里自己检查。
5. **`mct resume` 参数覆盖**：目前只能沿用 config；GUI 支持 override。
6. **原生工具 GUI 与 CLI 的一致性**：Homebrew GUI 的镜像/服务管理尚未进入 CLI；
   OCR GUI 的剪贴板/编辑能力无法在 CLI 复现。
7. **OCR 助手分发**：首次运行需要 `swiftc`；发布版应预编译并签名，避免用户装 CLT。

### P2（中长期）

1. 工具签名/公证、工具市场、版本升级/卸载。
2. JSON Schema `$id`/版本化、稳定的错误码枚举、结构化 `error.details`。
3. `mct install/uninstall`、工具依赖安装回滚。
4. 跨平台（Linux/Windows）CLI；当前依赖 macOS Vision/Keychain/brew。
5. 工具级并发锁（同一 jobDir 防重复运行）、幂等重试策略。
6. 把 `mct` 做成独立 Swift 可执行文件（复用 `ToolboxCore`），避免 Python 运行时依赖。

## 9. 第二轮：MCP 完整能力与跨进程调度统一（2026-10）

### 9.1 目标

在第一轮「有 CLI、有 Agent 目录」的基础上，补齐：

1. MCP 的 resources/prompts/progress/cancel；
2. CLI/Agent 与 GUI 的 GPU/网络/CPU 并发调度统一；
3. Agent 任务在 GUI 任务页实时可见、可取消、可打开产物；
4. 平台底层状态文件与心跳、崩溃后的可观察性。

### 9.2 共享任务状态

```text
$MCT_DATA_DIR/
├── Jobs/<jobID>/                # 真正的工作目录（config/log/产物）
├── AgentJobs/<jobID>/
│   ├── job.json                 # GUI/CLI 共享状态快照（原子写）
│   ├── events.jsonl             # 协议事件流（控制台回放）
│   └── cancel.request           # 取消请求
└── Locks/<resource>-<slot>.lock # 跨进程 fcntl 记录锁
```

`job.json` 字段：`status/progress/steps/artifacts/checkpoint/pid/error/jobDir/
source/batchID/createdAt/updatedAt/finishedAt/heartbeat` 等。
GUI 每秒轮询；CLI 通过 `mct jobs` 读取同一份文件。

### 9.3 跨进程资源调度

- Python `ResourceLocks` 与 Swift `CrossProcessResourceLocks` 使用同一套
  `Locks/<resource>-<slot>.lock`，双方都用 `fcntl(F_SETLK)`；
- 容量：`gpu=1`、`network=2`、`cpu=核数-1`；
- GUI 的 `ResourceScheduler` 在本地容量之外先拿跨进程锁，CLI 也走同一套；
- 进程崩溃时内核自动释放；等待期间状态为 `queued`，GUI 实时显示；
- `mct --no-locks` 仅用于调试，生产 Agent 不应使用。

### 9.4 MCP 能力

| 能力 | 实现 |
|---|---|
| tools/list | 5 个工具，inputSchema 来自 manifest |
| tools/call | 线程池异步执行；写 AgentJobs；输出 structuredContent |
| progress | 请求 `_meta.progressToken` → `notifications/progress` |
| cancel | `notifications/cancelled` → 取消排队/运行，返回 `-32800` |
| resources | `mct://tools`、`mct://tools/{id}`、`mct://jobs`、`mct://jobs/{id}`、`mct://paths` |
| resource templates | 工具/任务 URI 模板 |
| subscribe | `resources/subscribe` / `unsubscribe`；状态变化推 `notifications/resources/updated` |
| prompts | `run_tool`、`review_job`、`debug_tool` |
| logging | 工具 `log` 事件转 `notifications/message`（level/logger/data） |
| initialize | tools/resources/prompts/logging capabilities |

### 9.5 GUI 监控

任务页新增「Agent / CLI 任务」卡片：

- 进度条、状态、来源（CLI/MCP/批量/续跑）、当前步骤、检查点、错误；
- 「取消」写 `cancel.request`，执行进程轮询后终止子进程组；
- 「打开目录」进入真正的 `Jobs/<jobID>`；
- 「复制查看命令」复制 `mct jobs show <id> --json`；
- 「清理已结束」只删 `AgentJobs` 状态，不删任务产物；
- 菜单栏显示运行中的 Agent 任务数；
- 超过 90 秒没有 heartbeat 的活动任务显示「可能已中断」。

### 9.6 验证

- 单元测试：`python3 -m unittest discover -s Tests -v` → 11 tests OK；
- 跨进程锁：Swift 持锁时 Python 等待超时；Python 持锁时 Swift 等待超时；
- 并发：两个 `mct run demo.sleep`（gpu）第二个 `queued`，第一个结束后运行；
- 取消：`mct jobs cancel` → 退出码 5，状态 `cancelled`；
- MCP：progress 通知、tools/call、resources/read、prompts/get、
  notifications/cancelled 均通过；
- GUI：任务页截图确认 Agent 任务、进度、来源、状态和取消按钮可见；
- `./scripts/build_app.sh` 构建成功。

### 9.7 仍待改进

1. MCP `tools/list_changed` / `resources/list_changed` 尚未实现（catalog 当前按进程静态）；
2. AgentJobs 的 batch 父任务聚合、跳过项状态展示仍可细化；
3. GUI 对 heartbeat 超时目前只做展示，自动落盘 `interrupted` 依赖
   `mct jobs mark-interrupted`；
4. 跨进程锁超时后当前会记录日志并继续执行（避免 App 卡死），后续可增加
   「继续等待 / 失败」策略；
5. `mct` 仍是 Python 进程；Swift 化后可进一步共享模型与取消信号。
