# 热词与词表复用 · 评估与落地设计 v0.1

> 依据：`热词提炼与词表复用_技术设计_v1.md`（下称「原设计」）。
> 目标：在 MacToolbox 当前架构下，先把「热词注入 + 词表规则复用 + 可见可审」做实；
> 再决定是否投入自动提炼与拼音聚类。

---

## 1. 结论

### 1.1 应该先做哪一段

原设计的 P1–P3（Profile 数据结构、Session 词表、匹配与规则替换）**是收益最高、风险最低的一段**：

- 规则替换 0 token、毫秒级、可复现；
- 同一讲师/课程复用词表，直接消掉 60–70% 的已知错词；
- 匹配错误可以被用户一眼换掉；
- 不需要先解决「变体聚类」这个真正的难点。

P4（批量自动提炼）才是「自动学习」，依赖拼音/上下文聚类与标准形裁决，
在 8 GB 内存、本地优先的前提下，建议放到下一阶段，并先拿 7 集真实素材做准确率回归。

### 1.2 本版已经落地

| 能力 | 状态 |
|---|---|
| Session 热词（textarea，可手输/粘贴大纲） | ✅ |
| 内置/用户词表 Profile（JSON） | ✅ |
| Profile 自动匹配（文件名/目录关键词 + 讲师名） | ✅ |
| UI 显示匹配依据、可换/不用 | ✅ |
| 词表规则在 LLM 之前执行（0 token） | ✅ |
| 规则 + 修正留痕 `substitutions.json` | ✅ |
| LLM Prompt 预设 / 自定义 / 范围（全文/热词片段） | ✅ |
| 规则长串优先、单遍替换、用户修正优先 | ✅ |
| txt / csv / json 导入（预览、去重、错误、冲突） | ✅ |
| Profile 版本历史 / 回滚（非破坏式） | ✅ |
| 自动提炼（批量 ≥3） | ❌ 下一阶段 |
| 拼音聚类 / logprob 定位 | ❌ 下一阶段 |
| 单条规则禁用 UI / 版本 diff | ❌ 下一阶段 |

### 1.3 一句话架构

```
视频文件名 ──匹配──> Profile
Profile.hotwords ──合并 Session 热词──> whisper --prompt
Profile.rules ──合并 fixes.json──> make_srt（0 token）
                         │
                         └─ 剩余文本（可选只发热词片段）──> LLM 局部校对
```

## 2. 数据模型：为什么先 JSON，不急着 SQLite

原设计建议 SQLite + JSON 双份。当前规模（几十个 Profile、几百到几千条规则）下：

| 方案 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| JSON + 内存索引 | 可读、可 diff、可版本化、无迁移 | 大量规则时加载慢 | **当前** |
| SQLite 索引 | 查询/统计快 | schema 迁移、双份真相、调试麻烦 | 上万规则/多进程 |

建议：

- **Profile JSON 是唯一真相源**，继续保留；
- 内存中把规则按 `from` 建字典、按长度排序；
- 只有出现「上万条规则、按文件/规则筛选撤销、跨任务统计」时，再引入 SQLite **作为索引**，
  SQLite 从 Profile 重建，不反向写。
- 本版 `Profiles/*.json` + `records.json` 已满足 demo；未引入数据库。

迁移现有 169 条 `fixes.json`：

```json
{ "from": "财块", "to": "财会", "source": "user", "confidence": 1.0,
  "enabled": true, "scope": "global" }
```

- 长串规则原样保留（`这一个第一 → 这一个D1`）；
- 默认 `source=user`、`confidence=1.0`、`scope=global`；
- 先离线跑一遍，人工抽查 50 条，再启用。

## 3. 准确率设计（比 token 更重要）

### 3.1 标准形锚点

严格按原设计的优先级：

```
Session 用户词表 > 教材/大纲 > Profile > Global > LLM 裁决 > 集内频次
```

当前实现：

- Session 热词只影响 ASR prompt，不直接产生替换规则（避免把热词当标准形乱改）；
- Profile 规则是显式 `from → to`，不依赖频次；
- 用户 `fixes.json` 优先于 Profile（`prepare_profile_fixes` 里 existing 覆盖 rules）；
- LLM 只返回 `错误片段 → 修正`，不返回整篇改写。

### 3.2 单遍、长词优先

- `make_srt.py` 已经按 JSON 插入顺序应用；本版写入 `fixes.json` 前按 `from` 长度降序排序；
- 单遍替换，不做 `A→B`、`B→C` 链式；
- 不在替换结果上二次匹配。

### 3.3 自动匹配必须可解释

匹配信号（当前）：

- 文件名/目录命中 `fingerprint.filenameKeywords`（权重 0.6 × 命中比例）
- 讲师名命中 `teacherNames`（+0.25）
- 阈值 0.5；低于阈值不自动用

UI 显示：`ACCA FM · 示例词表 v1，依据：ACCA、FM、Financial management、Part B`，
并提供「不使用词表」「手动选择」「打开词表目录」。

> 原设计的 0.70 阈值更保守。当前 demo 只有单课程，取 0.5；
> 上线多课程后应上调到 0.65–0.70，并增加「转写后二次校验」。

### 3.4 不自动改人名

按原设计第 15 节：人名只提示不改。Profile 规则里可以显式写，
但自动提炼阶段不生成人名替换。

## 4. Token 设计：规则先行 + 可选片段

### 4.1 已实现

1. **规则先行（0 token）**：Profile 规则写入 `fixes.json`，LLM 看到的是已清洗文本；
2. **长串优先**，减少 LLM 重复判断；
3. **Prompt 预设**：通用 / ACCA / 访谈 / 只改术语，比一段大而全的 prompt 更聚焦；
4. **LLM 范围**：
   - `full`：全文，最准（默认）；
   - `hotwords`：只发送包含热词/英文缩写/数字的行，省 token，但可能漏改。
5. **无命中不调用**：`hotwords` 范围下没有命中行时直接跳过 LLM（0 token）。

### 4.2 尚未实现（下一阶段）

P6 的低置信过滤依赖 whisper.cpp 的置信度输出。原设计也把它列为开放问题：

- 需要确认 `-ls` / `--print-confidence` 的粒度是段级还是 token 级；
- 若是段级，只能做「段级过滤 + 拼音/词表近音候选」，不能做 token 级 diff；
- 建议先采集 7 集素材，统计 logprob 分布，再定阈值（不要拍脑袋）。

### 4.3 本版不承诺 70%

原设计的 ≥70% token 降低来自「规则 + 低置信过滤 + 局部 diff」组合；
本版只做了规则先行与可选片段范围。**没有实测 token 账单前，不宣称达到 70%。**
默认仍是全文校对，优先保证准确率。

## 5. 与当前 App 的映射

| 概念 | 实现 |
|---|---|
| Session 热词 | `hotwords` textarea（每行/逗号分隔） |
| Profile | `Tools/<tool>/profiles/*.json` + `Application Support/MacToolboxDemo/Profiles/*.json` |
| Global | 内置示例 Profile；后续可拆 `global.json` |
| 匹配 | `LexiconStore.match(path:toolID:)` |
| 规则合并 | `prepareJobValues` 写隐藏字段 `_lexiconRules` |
| 热词合并 | `_lexiconHotwords` + `hotwords` → `build_whisper_prompt` |
| 规则执行 | `prepare_profile_fixes` → `fixes.json` → `make_srt.py` |
| LLM | Prompt 预设/自定义 + `llmScope` |
| 留痕 | `substitutions.json`（from/to/count/source） |
| UI | 「词表 Profile」选择器 + 匹配依据 + 打开词表目录 |

### 导入与版本管理（本版补）

- 入口：设置 →「词表」→「管理词表…」；或工具设置里的「词表 Profile → 管理…」。
- 格式：
  - **txt**：一行一个热词；`错词 => 正确`、`->`、tab、逗号表示规则；`#` 注释。
  - **csv**：表头 `from,to`、`term` / `hotword`、`错词,正确`；支持引号；
    无表头时 1 列 = 热词，2 列 = 规则。
  - **json**：完整 Profile、`{hotwords:[], rules:[]}`、字符串数组、`{from:to}`、规则数组。
- 预览：热词/规则数、去重数、解析错误；确认时显示合并目标。
- 冲突：同名但目标不同的规则默认保留旧值；可勾选覆盖。
- 版本：
  - 当前文件 `Profiles/<id>.json`；
  - 历史 `Profiles/.history/<id>/vN.json`；
  - 有变化才生成新版本；回滚生成新的当前版本，不销毁历史；
  - 内置词表只读，先复制为我的词表。
- 新 Profile 的自动匹配关键词从词表名拆词生成；JSON 里带 `fingerprint` 则优先使用。

### Profile 示例

`Tools/media.subtitle.toolbox/profiles/acca-fm.json`

```json
{
  "id": "acca-fm-sample",
  "name": "ACCA FM · 示例词表",
  "version": 1,
  "tool": "media.subtitle",
  "fingerprint": {
    "filenameKeywords": ["ACCA", "FM", "Financial Management", "Part B"],
    "teacherNames": ["樊樊", "Flory"]
  },
  "hotwords": ["ACCA", "财务会计", "折现率", "摊销", "ROCE", "EPS"],
  "rules": [
    { "from": "折线率", "to": "折现率", "source": "user", "confidence": 0.99, "enabled": true }
  ]
}
```

## 6. 原设计 8 个问题的判断

1. **SQLite + JSON 双份是否必要？**
   当前不必要。JSON 唯一真相源 + 内存索引足够；上万规则/统计需求再引入 SQLite 作为只读索引。

2. **pypinyin + 编辑距离的假阳性率？**
   预计高（「开会/财会」这类同音不同义），必须叠加上下文相似度或 embedding。
   embedding 会引入模型/内存/延迟成本，不适合 8 GB 机器的 P1；建议 P4 先只做
   「用户词表 + 已有规则 + LLM 候选裁决」，拼音聚类作为实验开关，不默认开。

3. **低置信过滤的粒度？**
   需要先实测本机 whisper.cpp 构建的 `raw.json` 是否带 token 概率。
   若只有段级，降级为「段级筛选 + 近音候选」，不能承诺 token 级定位。

4. **JSON schema 还是 GBNF？**
   OpenAI 兼容服务的 structured output 支持不一。当前用「prompt 约束 + 宽松解析」，
   兼容性最好；本地 llama.cpp 可后续追加 GBNF。不要依赖所有供应商都支持 JSON schema。

5. **仅靠文件名/目录/时长的匹配准确率？**
   不够。当前只做「文件名/目录关键词 + 讲师名」，阈值 0.5，并强制 UI 可换；
   多课程后建议转写后做一次二次校验（热词命中率）再决定是否切换。

6. **300 条规则 × 2000 条字幕的性能？**
   Python `str.replace` 单遍几十万字符是毫秒级，不需要 Aho-Corasick；
   Aho-Corasick 留给「上万规则/超长文本」。当前实现按长度排序 + 单遍。

7. **169 条 fixes.json 迁移？**
   保留长串、`source=user`、`confidence=1.0`、`scope=global`；
   先跑 50 条抽检。`美股→每股` 这类短词建议默认禁用，只保留长上下文锚点。

8. **13 天估算？**
   P1–P3 在现有架构上约 3–5 天；P4（聚类 + 候选 + 结果页）最容易超时，
   建议先做「用户词表 + 规则复用」拿收益，再决定 P4。

## 7. 下一阶段建议

1. **Profile 管理 UI 补全**：导出 Profile、版本 diff、单条规则禁用/启用、备注。
2. **批量提炼**：只传候选词与频次，不上传全文；结果页必须人工确认；
   复用现有导入/版本/回滚。
3. **CSV 增强**：带换行的引号字段、更多表头别名。
4. **logprob 实测**：决定 P6 的低置信过滤是否值得做。
5. **自动替换准确率抽检**：50 条人工判定，目标 ≥98%；低于 95% 上调阈值。

---

## 8. 明确不做

- 不让 LLM 自由改写全文；
- 不自动修改人名；
- 不在单个视频任务中做自动提炼；
- 不把频次当标准形；
- 不在没有人工确认的情况下静默写入 Profile。
